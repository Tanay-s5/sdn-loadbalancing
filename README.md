# SDN Load Balancing

A Software Defined Networking (SDN) project that uses a Ryu controller to monitor traffic across two network paths and reroute traffic when a path becomes congested. The project uses Mininet and Open vSwitch to create a repeatable network experiment, then compares static routing with adaptive routing.

## 1. What It Does

The project creates a small network with three UDP clients, three UDP servers, four switches, and two paths between the clients and servers.

It supports two routing modes:

| Mode | Behaviour |
|---|---|
| `static` | Keeps the initial client-to-path assignments during the experiment. |
| `adaptive` | Monitors traffic and can move a client flow to the other path when the current path becomes congested. |

The experiment sends normal traffic from all three clients. One selected client temporarily increases its packet rate to create controlled congestion. The scripts collect packet-level data and compare the behaviour of the two routing modes.

## 2. Network Topology

The topology is a diamond-shaped network:

```text
 h1    h2    h3
  \     |     /
       s1
      /  \
     /    \
    s2    s3
     \    /
      \  /
       s4
    /   |   \
   h4   h5   h6
```

The actual paths are:

| Path | Route | Bandwidth | Delay |
|---|---|---:|---:|
| A | `s1 -> s2 -> s4` | 5 Mbps | 5 ms per link |
| B | `s1 -> s3 -> s4` | 10 Mbps | 2 ms per link |

Each client is paired with one server:

| Client | Server | Initial path |
|---|---|---|
| `h1` | `h4` | A |
| `h2` | `h5` | B |
| `h3` | `h6` | A |

The initial path assignments are defined in `controller.py`. Link bandwidth and delay are defined in `topo.py`.

## 3. Technologies Used

| Technology | Purpose |
|---|---|
| Python 3 | Controller, traffic generator, receiver, experiment runner, and analysis scripts |
| Ryu | SDN controller that installs and updates OpenFlow rules |
| OpenFlow 1.3 | Protocol used by Ryu to communicate with the switches |
| Mininet | Creates the virtual hosts, switches, and network links |
| Open vSwitch | Provides the virtual switches used by Mininet |
| UDP sockets | Generate and receive test traffic |
| Matplotlib | Optional plots generated by the analysis script |

## 4. How It Works

1. `topo.py` creates the Mininet topology with four Open vSwitch switches and six hosts.
2. `controller.py` connects to the switches using OpenFlow 1.3 and installs the initial forwarding rules.
3. The controller periodically requests flow and port statistics from switch `s1`.
4. It calculates each client's traffic rate and estimates the utilization of paths A and B using their configured capacities.
5. In adaptive mode, the controller checks whether a path remains above the congestion threshold for the configured number of samples.
6. If a suitable client flow can be moved without pushing the destination path above the threshold, the controller updates the forwarding rules on `s1` and `s4`.
7. `client.py` sends UDP packets containing a sequence number and send timestamp. `server.py` receives the packets and records packet counts, loss information, throughput, and timestamps.
8. `run_experiment.py` runs the selected routing modes and saves the logs. `analyze.py` compares the results.

The adaptive controller does not automatically move a flow back to its original path when congestion clears. The updated path assignment remains in place for the rest of that controller run.

## 5. Requirements

The project is intended to run on a Linux machine because Mininet and Open vSwitch require system-level networking support.

Required software:

- Python 3
- Mininet
- Open vSwitch
- Ryu with OpenFlow 1.3 support

Optional software:

- Matplotlib, for generating `comparison.png`

There is no `requirements.txt` in the repository. Install the system packages using your distribution's package manager and install Ryu in a Python environment that is available to the `ryu-manager` command.

For Debian or Ubuntu-based systems, the system packages can typically be installed with:

```bash
sudo apt update
sudo apt install mininet openvswitch-switch python3-pip
```

Install Ryu and the optional plotting dependency in the Python environment used by the project:

```bash
python3 -m pip install ryu matplotlib
```

Check that the tools are available:

```bash
python3 --version
mn --version
ovs-vsctl --version
ryu-manager --version
```

## 6. Setup

Clone the repository and enter the project directory:

```bash
git clone https://github.com/Tanay-s5/sdn-loadbalancing.git
cd sdn-loadbalancing
```

Mininet requires root privileges. The experiment runner needs to find `ryu-manager` when it is started with `sudo`. The command below preserves the current `PATH`:

```bash
sudo env "PATH=$PATH" python3 run_experiment.py
```

The topology helper is already implemented in `topo.py`. The runner imports `topo.CONTROLLER_PORT` to start Ryu and calls `topo.make_net()` to create the Mininet network. No manual topology code changes are required before running the experiment.

## 7. Running an Experiment

### Run static and adaptive modes

By default, the runner executes both modes in sequence and then runs the analysis:

```bash
sudo env "PATH=$PATH" python3 run_experiment.py
```

### Run only one mode

Run only adaptive routing:

```bash
sudo env "PATH=$PATH" python3 run_experiment.py --modes adaptive
```

Run only static routing:

```bash
sudo env "PATH=$PATH" python3 run_experiment.py --modes static
```

### Run with custom traffic and controller settings

For example, run a 60-second experiment with a congestion burst between 15 and 45 seconds:

```bash
sudo env "PATH=$PATH" python3 run_experiment.py \
  --duration 60 \
  --base-pps 150 \
  --burst-pps 450 \
  --burst-client 3 \
  --burst-start 15 \
  --burst-end 45 \
  --threshold 0.80 \
  --poll-interval 0.25
```

The runner starts the controller, creates the topology, checks connectivity, starts the UDP servers, starts the clients concurrently, and collects the resulting logs.

If `ryu-manager` is not found when running with `sudo`, pass its full path with `--ryu-cmd`:

```bash
sudo env "PATH=$PATH" python3 run_experiment.py \
  --ryu-cmd /full/path/to/ryu-manager
```

If an experiment is interrupted, clean up Mininet before starting another run:

```bash
sudo mn -c
```

## 8. Configurable Parameters

### Experiment runner: `run_experiment.py`

These options can be passed on the command line.

| Parameter | Default | Description |
|---|---:|---|
| `--modes` | `static adaptive` | Routing modes to run. Accepted values are `static` and `adaptive`. |
| `--outdir` | `results` | Directory used to store experiment output. |
| `--duration` | `40` seconds | Duration of each client's traffic generation. |
| `--base-pps` | `150` | Normal packet rate for each client, in packets per second. |
| `--burst-pps` | `450` | Packet rate used by the selected client during the congestion burst. |
| `--burst-client` | `3` | Client that creates the burst. Accepted values are `1`, `2`, or `3`. |
| `--burst-start` | `10` seconds | Time after the client starts when the burst begins. |
| `--burst-end` | `30` seconds | Time after the client starts when the burst ends. |
| `--size` | `1200` bytes | UDP payload size. |
| `--report-interval` | `0.5` seconds | Interval between server throughput reports. |
| `--ryu-cmd` | `ryu-manager` | Command used to start the Ryu controller. Can be a full path. |
| `--controller-wait` | `3` seconds | Time to wait for Ryu to start. |
| `--poll-interval` | `0.5` seconds | Interval between controller statistics polls. |
| `--threshold` | `0.85` | Congestion threshold as a fraction of path capacity. For example, `0.85` means 85%. |
| `--confirm-samples` | `2` | Number of consecutive samples required to confirm congestion. |
| `--cooldown` | `5` seconds | Minimum time between adaptive rerouting decisions. |
| `--delay-limit-ms` | `50` ms | Delay limit used by the analysis when deciding whether a packet is late. |
| `--no-analyze` | Off | Skip the automatic analysis step after the experiment. |

The runner validates that `--burst-start` is greater than zero, `--burst-end` is after the start, and the burst ends no later than `--duration`.

### Traffic generator: `client.py`

These options control an individual UDP client.

| Parameter | Default | Description |
|---|---:|---|
| `--server` | Required | Destination server IP address. |
| `--port` | `5000` | Destination UDP port. |
| `--duration` | `20` seconds | How long the client sends traffic. |
| `--pps` | `500` | Packet rate in packets per second. |
| `--size` | `1200` bytes | UDP payload size. Must be between 12 and 65,507 bytes. |
| `--profile` | None | Optional time-based packet-rate profile, such as `0:150,10:450,30:150`. |
| `--summary-json` | None | File path for the client's start time, end time, and packet counters. |

Example:

```bash
python3 client.py --server 10.0.0.4 --duration 40 --pps 150 \
  --profile "0:150,10:450,30:150" --size 1200
```

### UDP receiver: `server.py`

| Parameter | Default | Description |
|---|---:|---|
| `--port` | `5000` | UDP port on which the server listens. |
| `--bind` | `0.0.0.0` | Local address to bind to. |
| `--report-interval` | `1.0` second | Interval between throughput reports. |
| `--log-prefix` | None | Prefix for packet CSV and summary JSON output files. |

### Controller settings: `controller.py`

The experiment runner passes the first four settings through command-line options. The controller reads them from environment variables.

| Environment variable | Default | Description |
|---|---:|---|
| `ROUTING_MODE` | `adaptive` | Selects `static` or `adaptive` routing. |
| `POLL_INTERVAL` | `0.5` seconds | Statistics polling interval. |
| `CONGESTION_THRESHOLD` | `0.85` | Path utilization above which congestion is detected. |
| `CONFIRM_SAMPLES` | `2` | Consecutive over-threshold samples required for confirmation. |
| `REROUTE_COOLDOWN` | `5.0` seconds | Cooldown after a reroute. |
| `RESULTS_DIR` | `results` | Directory for controller logs. |

### Network constants: `controller.py` and `topo.py`

These values are currently hard-coded and must be edited in the source files if the network design changes.

| Constant | Current value | File | Description |
|---|---|---|---|
| `PATH_CAPACITY_MBPS` | A: `5.0`, B: `10.0` | `controller.py` | Capacity used to calculate path utilization. Keep this consistent with the bandwidth configured in `topo.py`. |
| `CLIENT_PATH` | h1: A, h2: B, h3: A | `controller.py` | Initial path assignment for each client. |
| `MIN_FLOW_MBPS` | `0.05` | `controller.py` | Minimum measured flow rate considered for rerouting. |
| `UPLINK` | A: port `4`, B: port `5` | `controller.py` | Uplink ports on switch `s1` used to identify the two paths. |
| `PRIORITY` | `200` | `controller.py` | OpenFlow rule priority used by the controller. |
| `MONITORED_DPID` | `1` | `controller.py` | Switch datapath ID whose flow and port statistics are monitored. |
| `CONTROLLER_IP` | `127.0.0.1` | `topo.py` | IP address used by Mininet's remote controller connection. |
| `CONTROLLER_PORT` | `6653` | `topo.py` | OpenFlow TCP port used by the runner and Mininet switches. |
| `PATH_A_BW_MBPS` | `5` Mbps | `topo.py` | Bandwidth of each inter-switch link on path A. |
| `PATH_A_DELAY` | `5ms` | `topo.py` | Delay on each inter-switch link on path A. |
| `PATH_B_BW_MBPS` | `10` Mbps | `topo.py` | Bandwidth of each inter-switch link on path B. |
| `PATH_B_DELAY` | `2ms` | `topo.py` | Delay on each inter-switch link on path B. |
| `QUEUE_PACKETS` | `100` | `topo.py` | Maximum queue size in packets on each inter-switch link. |
| Host addresses, MAC addresses, and ports | `10.0.0.1` to `10.0.0.6` | `topo.py`, `controller.py` | Must match between topology and controller definitions. |

When changing the topology, update the host and port mappings in both `topo.py` and `controller.py`. Also update `PATH_CAPACITY_MBPS` to match the link bandwidth configured in Mininet.

## 9. Analysing Results

The experiment runner automatically calls `analyze.py` unless `--no-analyze` is supplied.

To run the analysis separately:

```bash
python3 analyze.py --results results
```

Useful analysis options:

| Parameter | Default | Description |
|---|---:|---|
| `--results` | `results` | Directory containing the experiment runs. |
| `--modes` | Detected automatically | Run folders to compare, such as `static adaptive`. |
| `--delay-limit-ms` | `50` ms | Maximum one-way delay accepted before a packet is counted as late. |
| `--no-plot` | Off | Generate summary tables without creating a plot. |

The analysis reports:

- Total packets sent and overall packet loss.
- Packet loss during the congestion window.
- Mean, 95th-percentile, and maximum one-way delay during congestion.
- Time taken by the controller to detect congestion and issue a reroute.
- Flow-rule installation time.
- Data-plane recovery time and whether recovery happened before the burst ended.

A packet is considered bad if it is lost or its one-way delay exceeds `--delay-limit-ms`. Recovery time is measured from congestion onset to the send time of the last bad packet across the flows.

The default output directory is `results/`.

```text
results/
├── static/
│   ├── scenario.json
│   ├── ryu.log
│   ├── controller_events.jsonl
│   ├── controller_stats.csv
│   ├── h4_packets.csv
│   ├── h4_summary.json
│   └── ...
├── adaptive/
│   ├── scenario.json
│   ├── ryu.log
│   ├── controller_events.jsonl
│   ├── controller_stats.csv
│   ├── h4_packets.csv
│   ├── h4_summary.json
│   └── ...
├── summary.csv
├── summary.json
└── comparison.png
```

The receiver creates packet CSV and summary JSON files for each server. The controller creates event and statistics logs for each routing mode. The analysis script creates the combined summary files and, when Matplotlib is installed, the comparison plot.

**Note:** Each run recreates its corresponding `results/static/` or `results/adaptive/` directory. Copy or rename previous results before rerunning an experiment that uses the same output directory.

## 12. Limitations

- This is a Mininet-based experiment, not a deployment on a production network.
- The topology, host mappings, path capacities, and initial routes are designed for the current six-host, four-switch setup.
- The adaptive controller considers the configured path capacities and measured flow rates. It does not implement a general-purpose routing protocol.
- Adaptive rerouting changes the affected client's path but does not automatically restore its original path after congestion clears.
